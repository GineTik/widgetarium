# What a screen draws when there is nothing to draw, and while it waits

Apple HIG, Material 3 / M2 / M1, NN/g, four enterprise design systems that publish real rules (IBM Carbon, AWS Cloudscape, PatternFly, GitLab Pajamas, Atlassian), and nine products. Obsidian's own rules were extracted from the shipped `obsidian-1.13.7.asar`, so they are verified against the binary rather than described.

## The five findings that change an engine's design

**1. The region survives; the widget's own chrome inside it does not.** Carbon: the empty state should "replace the element that would ordinarily show" — for a table, the column headers and footer go too, so a screen reader does not read an entire empty table before reaching the message. This cuts exactly where a drop-target engine needs it: **the box keeps its space, its heading and its geometry; the widget's internal header row is what disappears.** A region that vanishes when empty can never receive the first drop, and no source tells you to make the region vanish — what they remove is one level down.

**2. The loading thresholds are published, numeric, and three independent sources agree.** Material 3, on two separate pages: under **200 ms** show no indicator; **200 ms – 5 s** a loading indicator; **over 5 s** a progress indicator. NN/g independently: under 1 s nothing, 2–10 s a looped animation, 10 s+ percent-done. Obsidian implements **300 ms** in CSS. This is the one part of the problem **the engine should own outright** — a timing rule, not a content rule, and no widget should be allowed to decide it.

**3. How many regions are empty at once is a board-level fact, and it changes what each one draws.** Carbon: on a dashboard where several widgets fail, repeated illustrative icons lose their effect, so text-only is preferable; and when several empty states can show at once the call to action should be **tertiary**, so the screen does not sprout N primary buttons. **Only the engine knows N.** This is the strongest published argument that empty-state rendering belongs to the engine and not to the widget — a widget cannot know how many of its siblings are also empty.

**4. "Empty" and "filtered to nothing" are two states with two different mandatory actions, and the engine already knows which is which.** Cloudscape separates *empty state* (nothing ever created, or all deleted) from *zero results* (a filter matched nothing) and fixes the action for each: empty offers create; zero-results offers **Clear filter**, always that wording, always secondary, and the resource counter stays visible showing 0 of the real total — which is what tells the person the data still exists. GitLab Pajamas goes further: "No results found", **no CTA at all**. An engine that resolves a prop's gateway knows whether a `where` was applied; the widget never has to be asked.

**5. Everything is derivable except the shape of the placeholder.** Apple's Widgets guidance is the only first-party rule aimed at exactly this engine's problem: a widget shows placeholder content while data loads, built from static interface components plus semi-opaque shapes — rectangles of varying widths for lines of text, circles or squares for glyphs — and the placeholder must make the widget **recognisable**. NN/g says the same and names the failure: a "frame-display" skeleton showing no layout information is not a progress indicator. Recognisability is a fact about the widget's own composition, so **the manifest has to carry it**.

## The answers, per question

**An empty region inside a populated screen.** Per-region empty states are published doctrine. Carbon places them in the otherwise-empty space, in the context of the missing data, across dashboards, tables, tiles, full pages and side panels. PatternFly sizes them by container — extra-small inside cards, small inside tables and modals, large for a full page — and forbids toolbars or filters in a full-page empty state, because there is nothing to filter. Carbon adds a rule for small regions: elements are left-aligned as a block, **except in a small tile, where the image is centred above left-aligned text**, deliberately, so the empty state does not read as content and get skipped. Content is a title, optional body, optional single action; if space is limited, text only.

Asana's board keeps empty sections and they remain drop targets — sections must be emptied before they can be deleted. Trello keeps empty lists. **Notion is the only counter-example and makes it a user setting** ("hide empty groups" in board view; the toggle's exact wording is unverified).

**First run.** The published difference is not "bigger" — it is a different *kind* of content. M2 names two alternatives: **starter content** (demonstrates the primary features, personalised if possible, and deletable) and **educational content** (dismissible, brief, contextual to this screen, explicitly not whole-app onboarding). Carbon's deciding axis is primary versus secondary feature: a primary feature earns education, a secondary one gets a basic empty state. Carbon also names the trap — if starter content can be deleted, the basic empty state is still needed as a fallback. Apple separates three things routinely confused: a launch screen is not onboarding and not a splash screen, must be nearly identical to the first real screen, and carries no text (it cannot be localised) and no branding; onboarding is optional and comes after; non-essential setup is postponed in favour of good defaults. Apple's stronger recommendation is context-specific tips placed beside the thing they describe, rather than one upfront flow.

**Loading.** Skeletons, not spinners, for anything arriving with a known shape. Apple: show something as soon as possible, because a blank screen reads as a broken app; keep the indicator moving, because a stationary one reads as a stall; prefer determinate; indeterminate→determinate is allowed, circular→bar is not; avoid vague labels like "loading", which add nothing. M3 supplies the placement rules an engine needs: **one indicator for a group of loading items, never one per item**; a linear indicator at the top of the page means the whole page, attached to a card's edge means that card only; a circular indicator is centred on the container that is loading; and when loading *more* rows the indicator goes in the empty space where the new content will appear and must not overlap what is already there. NN/g: under 1 s a skeleton is actively harmful — the flash makes people feel they cannot keep up.

**Error and partial failure.** Failure is local. Cloudscape separates component-specific functional errors from page-level failures and shows the error where it occurred; Material 1's archived pattern says the person should still be able to use as much of the rest of the app as possible, and that a failed load is drawn as an empty state for that content. **The systems contradict each other on one point**: Carbon treats error as a third class of empty state (permissions, systems issue, configuration required, action not supported — plain language, no codes, a corrective step where one exists), while Cloudscape says not to use empty states for errors at all and to use a page-level flashbar instead. **For a board of independent tiles Carbon wins by construction**: a page-level flashbar cannot say *which tile* failed.

**Row-level states.** M3 publishes the only concrete rule found, and it is per-layout rather than per-row: there may be only **one** hover, one focus, one pressed and one dragged state in a layout at a time, and those may combine with each other and with selected. Disabled is the exception allowed to fail contrast, and cannot be focused, dragged or pressed. Dragged states are specified as *low* emphasis so the drag does not distract. Without colour: **WCAG 2.2 SC 1.4.1 (Level A) is normative** — colour must not be the only visual means of conveying information — and Apple operationalises it with a green circle *carrying a checkmark* versus a red octagon *carrying an X*. Apple also distinguishes two selection idioms an engine must choose between: a navigational list highlights the selected row **persistently**, to show the path taken; a list of options highlights briefly and leaves a checkmark.

## Obsidian's implementation is worth copying wholesale

All verified from `app.css` in the shipped binary.

- **Two tiers, which is exactly what a board needs.** `.pane-empty` is a centred, faint, small line of text with an optional actions block — the *region* empty state: one sentence, in place, no illustration. `.empty-state` is absolutely positioned at full width and height, flex-centred, with an h2-sized title and a list of accent-coloured actions — the *whole leaf* empty state. And `.search-empty-state` is faint, small and **left-aligned with a start padding, not centred**: an empty result list inside a pane does not get the centred treatment.
- **The strings are derived mechanically from what the pane is**: "No backlinks found.", "No tags found.", "No results found.", "No matches found.", "No recent files.", "No headings found.", "No bookmarks found." One sentence, no illustration, no CTA.
- **Loading is a 300 ms-delayed 3px accent bar scoped to the region** — `animation: 1000ms ease-in-out 300ms infinite progress-bar`, on `.search-result-container.is-loading` and friends, never on the window.
- **Drag targets a whole region**: a 10% accent overlay across the entire view.
- **The precedence rule nobody else publishes**: every hover rule is guarded by `body:not(.is-grabbing)`, so **hover feedback is suppressed everywhere while a drag is in progress.** That single guard resolves "how many states can a row show at once" at the body, not per component.

## Synthesis: four of five states are computable

| What | Derived from | Licensed by |
|---|---|---|
| Which state applies | gateway status + whether a `where` is active + whether the binding ever held rows | Cloudscape's empty-vs-zero-results split |
| Whether to draw anything yet | elapsed ms against 200 ms / 5 s | M3's table; Obsidian's 300 ms |
| Where the indicator goes | the box being loaded — edge for a region, centred for a container, in the space where new rows will appear | M3 placement rules |
| Size and form of the empty content | the box's measured size → text only / text + icon / full block | PatternFly's ladder; Carbon's "if space is limited, just text" |
| Illustration or not; primary or tertiary action | **count of empty siblings on this board** | Carbon's multiple-empty-states rules |
| The heading | the prop's label and the widget's `role` — "No " + the collection's label is Cloudscape's own formula, and Obsidian's shipped strings are that formula per pane | Cloudscape, corroborated by Obsidian |
| The action, or none | the widget's `writes` filtered through `can()` | Carbon's "don't lead into a dead end" + Cloudscape's "always an action, or a link" |
| The filtered-to-nothing action | clear the engine's own `where` | Cloudscape's fixed Clear filter |

**The sharpest consequence for this codebase:** an empty state offering "Create" on a binding whose `allow` omits the create verb is a dead end every system forbids, and only the engine can see both facts at once. Deriving the action from `writes ∩ allow` makes the dead end **unrepresentable rather than merely discouraged** — an invariant in the writer rather than a check on the way in.

Must be authored per widget: **the placeholder's shape** (Apple's recognisability, NN/g's structure-mimicking — belongs in the manifest beside the component); **one optional sentence**, only where the reason for emptiness is not obvious (Cloudscape's default is none, and Obsidian ships a whole product with no descriptions anywhere); **first-run and starter content**, for the few widgets that are a primary feature; and **domain-specific error remediation text**.

One conflict to settle rather than average: Carbon's replace-the-element rule, applied naively to a board, would remove the region. It must not. In a board whose region titles are markdown nodes standing beside the tile — which this project already specifies — Carbon's rule lands on the widget's *internal* header row and nothing else. The box, its surface, its space and its heading stay, which is what keeps it droppable.

## Negative findings

1. **Neither Apple nor Material 3 publishes an empty-states page at all.** Apple never had one (the HIG endpoint 404s, and nothing appears in the adjacent pages). Material had one in M1 and M2 and **dropped it in M3**; M3's only empty-region rule is one sentence inside the list-detail layout page. The two most-cited systems in the industry have the least to say, and the real doctrine lives in enterprise systems nobody cites for it.
2. **Nobody publishes whether an empty region keeps its space** in a flexible layout — whether siblings reflow into it. M3's list-detail note is the single exception and covers one arrangement.
3. **Nobody publishes how an empty region behaves as a drop target.** Not Carbon, not Material, not Atlassian — whose own product is a kanban board. **Obsidian's shipped CSS is the only artefact in this survey that answers it, and it answers in code, not prose.** That Asana users keep asking to hide empty sections and are not given the option is the closest thing to evidence that the industry default is "keep it".
4. **Nobody publishes a timeout** — how long a skeleton may stand before the state must flip to error. M3 caps the indicator *choice* at 5 s and NN/g at 10 s, but both are about which animation to draw.
5. **Nobody publishes a cap on simultaneous row states**, nor a precedence order when they combine. Obsidian's `is-grabbing` guard answers a question no specification asks.
6. **Nobody publishes a non-colour encoding for domain severity** — overdue, at-risk, blocked, stale. WCAG forbids colour alone and Apple suggests shape or icon, but no system in this survey names a vocabulary. **Whatever this engine chooses here is original work, not prior art.**
7. **No product documents its own empty, loading or error rules.** Not Linear, not Notion, not Things, not Todoist, not Height. Superhuman's post on choosing Inbox Zero photographs is the only first-party product writing found on the subject in the whole survey, and it is about photograph selection. Height has no discoverable design documentation at all and was dropped rather than described from screenshots.
