The task dialog

One surface replaces task-popup, task-properties and task-comments. Left: the title, the tags, the note body. Right: a plate of properties that belongs to the board, not to the task — every task on this board shows the same rows, and the rows nobody has filled in yet are shown too, because filling one in is how it gets created.

The arrangement

Wide: the plate sits beside the note

Nothing is being saved here. The title is a caret you type into, a tag opens a picker, a number is dragged. Priority is shown mid-edit — pressed, the row lifts off the plate onto the dialog's own surface and its list opens under it. The description carries its own Preview / Detail switch at the top right.

Why one surface

Three widgets read the same frontmatter separately and drew the same status three different ways. The popup owned the header, the properties list owned the fields, the comments panel owned the footer — and none of them owned the note.

  • one read of the note, one place that writes it back
  • properties come from the board, never from a per-widget setting
  • comments arrive after this is agreed, not with it

The board's list is declared once, in the board block:

Expand, then close — in that order, top right. Close is the terminal one, so it takes the extreme corner where the hand goes without looking. The board's name shares that strip. It is the one thing on screen that explains why these particular rows are here — the property list belongs to it. Nothing else joins the strip; if this reads as clutter, it can go and the two controls sit alone.

The idea underneath

The list belongs to the board

A task does not carry a set of properties. The board carries one list and every task on it shows those rows — filled, or reading Empty. Adding a property adds a row to every task at once; nothing has to be back-filled, because an unset row is a legal state rather than a missing one.

The empty state is the common one, not the exception — a new board has seven rows and none of them filled. So it is drawn as a real, pressable row with a faint Empty, at the same height as a filled one. It is never hidden behind an "add a value" affordance, because that would make the board's list invisible on exactly the task that most needs to see it.

The property system

The name decides the control

Certain names are anchored: whatever a property called Priority holds, it is drawn and edited as a priority. The anchor applies the moment the name is typed and forever after — there is no type to pick and no type to change. Every other name falls through to plain text.

The payoff

The same list is the filter

Nothing below was configured. The filter's rows are the board's property list, and the control on each row is the one its name already anchors — a date range for Deadline, tags for Approval and Priority, avatars for Members, a range for Progress. Add a property and it is filterable that second.

The description

Two modes, one switch

Preview is what Obsidian renders — read mode, plugins' output included. Detail is the raw note in a plain text box, every marker still on screen, made readable by weight and colour and nothing else. Plain text is honestly unreadable; this is the minimum that fixes that, and it is deliberately not live preview.

The switch · the kit's segmented capsule, at the description's top right

Two states of one control the kit already owns. It is the same capsule the board uses for its view tabs, at the small size — nothing new is invented for the dialog, and the pair sits at the description's top right so it never competes with the title.

The constraint, not papered over

A textarea cannot style its own text

There are no elements inside a <textarea> — only characters. So coloured-but-plain text is always one of two mechanisms, and they cost different things. The Detail specimens above are drawn as mechanism 1.

1 · Transparent textarea over a styled mirror Drawn above

The real <textarea> sits on top with transparent text and a visible caret; underneath, the same string is rendered into spans and coloured.

Buys: native editing, native selection, native undo, native spellcheck, and the content stays genuinely plain.

Costs: font, size, line height, letter spacing, padding, border and wrapping must match exactly, and the two must scroll as one — any drift and the characters visibly separate.

2 · contenteditable

One element that is both the text and the styling; the spans are the content.

Buys: styling is trivial, there is nothing to keep in sync, and nothing can drift.

Costs: the browser decides what a paste and what an Enter insert — keeping the content genuinely plain becomes the ongoing work, and re-styling as you type means moving the caret back.

Expand is still the way to the real editor. Detail lets you fix a line without leaving the dialog. It is not live preview, it has no hotkeys and no plugins — when the body needs actual work, expand goes to the note's own page, where Obsidian's editor, the outline and the backlinks are.

Both themes, at once

It holds either way round

Not the viewer's theme — both, side by side. Every colour is a token; the plate is --wg-fill against a --wg-surface dialog, which is one step of contrast in light and one step in dark.

Before you say yes

Calls I made that you did not specify

Each of these is a decision the brief left open. They are drawn above rather than left blank, so the page is honest about what it is proposing — but any of them can go the other way without touching the rest.

The board name in the top stripYou asked for two controls in the corner and nothing else. I put the board's name at the left of the same strip, because it is what owns the property list. Remove it and the strip is two circles on the right.
The plate keeps 22 px, not 8The kit's concentric rule would make an inset panel's radius the dialog's 28 minus its 20 px padding. You asked for it to read as a kanban column, so it keeps the board's 22. The two curves are 20 px apart, which is enough that they never read as a pinched pair.
Progress is a track, not a stepperYou said "drag or type a number". I drew the track inside the row, so the whole plate can be skimmed. A stepper capsule (− 65 +) would be a legitimate alternative and takes less width.
Members store as plain namesThere is no people type in Obsidian, so something has to be invented. I chose a plain list of names in frontmatter with the avatar drawn from it, so a hand-edited note still makes sense. The alternative — storing links to person notes — is richer and breaks plain editing.
The unset word is "Empty"Obsidian's own property editor says Empty. The alternatives are a dash, or the property's own hint ("No deadline"). I took Obsidian's word so the dialog does not invent vocabulary.
Anchors are case-insensitive on the whole namedeadline, Deadline and DEADLINE all anchor; Deadline (soft) does not, and falls through to text. Whether near-misses should anchor is a real question I could not answer for you.
Assignees is an alias, not a second anchorYou wrote "Members (or Assignees)". I read that as one anchor with two accepted names, so a board can call it either and get the same control. If they are meant to be two separate properties, that changes.
Detail mode is drawn as the mirrorA transparent textarea over a styled copy of the same text. It keeps native editing and plain content; a contenteditable would be far simpler to style and far harder to keep plain. The page states the cost of each rather than choosing — this one is yours.
Inline code in Detail: bold or plain"Text marked with a border" reads as inline code or as the bold markup itself. Both readings are drawn side by side above, labelled A and B. Everything else about Detail is identical either way.
Hashtags in Detail stay plainLinks get the accent because you named them. #orbitask is left as ordinary text — colouring it would be a fourth rule nobody asked for, and the tags already have their own row above the description.
