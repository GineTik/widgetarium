# A gateway's record type is its contract

`PROPOSED` · 2026-09-02 · answers the field-list question left open by `docs/typed-widgets.md`

## TL;DR

One rule: **the record type a gateway carries is the list of needs.** Each property is a need, `?`
makes it optional, `Aka<…>` names what that need may already be called in a stranger's vault. The
build reads the type and writes the manifest; the engine resolves each need against the folder's own
fields and asks about only the ones it cannot resolve.

## The rule, in one file

```ts
import { createWidget, useData } from "widgetarium";
import type { Action, Aka, CollectionGateway, Color, Day, ListAction, Ref, RemoveAction, Text, UpdateAction } from "widgetarium";

type Habit = {
	days: Day[] & Aka<"entries" | "dates" | "log" | "checkins">;
	title?: Text & Aka<"name">;
	color?: Color;
	goal?: number;
};

type Accesses = {
	list: ListAction;
	update: UpdateAction;
	remove?: RemoveAction;
	archive?: Action<Ref, void>;
};

export default createWidget(function HabitGrid({ habits }: { habits: CollectionGateway<Habit, Accesses> }) {
	const { rows } = useData(habits.list);
	return rows.map((habit) => habit.days.length);
});
```

| written | read as |
|---|---|
| a property | a need |
| `?` | optional — the widget draws without it |
| no `?` | required — an unresolved one is the tile's one question |
| `Day`, `Text`, `Color`, `number`, `boolean` | the type the field picker filters by |
| `T[]` | many |
| `Aka<"a" \| "b">` | the names this need answers to |
| `CollectionGateway<T, Accesses>` | the gateway, and the verbs the widget reaches it through |
| `ListAction` … `RemoveAction` | the engine's own verb — its signature comes from `T`, never written by hand |
| `Action<I, O>` | a verb beyond the standard five, its signature written here |
| a verb without `?` | a binding that cannot do it may not host this widget |
| a verb with `?` | the widget mounts anyway and asks `can()` before drawing the control |

`?` carries one meaning in both halves: **the widget survives without it.**

`Aka<_Names extends string> = unknown`, so `Day[] & Aka<…>` **is** `Day[]` to the checker and to the
widget. It costs nothing at runtime and changes no type. The build reads the syntax, not the
resolved type.

The label under which a need appears in the picker is its own name, humanised — `days` becomes
`Days`. A need whose name does not say what it is has the wrong name.

## Why not a decorator

A decorator attaches to a class or a class member. A record type is neither, so there is nothing for
one to sit on, and making every widget author a class to gain a place for a label would change the
authoring model to carry an annotation. The generic argument carries the same fact with no class and
no runtime.

## Why the build reads it, and not the engine

Settled in `docs/typed-widgets.md`: every transpiler erases types, sucrase included —
`src/registry.js:22` compiles a widget with the `typescript` transform, which strips and checks
nothing. So the type is a build-time fact and the manifest stays the runtime one, autogenerated from
here on.

Reading the declaration needs a compiler, and it is a devDependency the build script imports — no
widget source ever sees it. `typescript@7.0.2` is installed today and publishes its API only under
`typescript/unstable/*` (verified: `node_modules/typescript/package.json` `exports`); a release
build reading types through an API its own vendor labels unstable breaks on a patch bump. So: one
`typescript@5`, doing both `tsc --noEmit` and the manifest reader. The native port's speed is what
is given up, on a check that takes seconds here.

## What the engine does with the needs

`fieldsOf()` in `src/gateway/fields.ts` reports `{ prop, type, values }` per field, read off the
records themselves. Obsidian's own registry — `.obsidian/types.json`, reachable through
`app.metadataTypeManager` — supplies what a property was declared as. A need is resolved against
both:

| step | rule | example |
|---|---|---|
| 1 | exact name | `days` → `days` |
| 2 | `was` — the need's own previous name | the lazy-migration law |
| 3 | `Aka`, then fuzzy over those names | `days` → `entries` |
| 4 | the sole field of the required type | one `Day[]` in the folder, so it is the one |
| 5 | otherwise, unresolved | the tile asks, once |

Steps 1–4 are silent and are **never written down**. Only an answer to step 5 is stored, and it is
stored per folder, not per tile:

```
shapes["Habits"] = { days: "entries", goal: "target" }
```

The first widget bound to `Habits` asks. Every widget bound there afterwards is silent. A tile may
override its own reading, which is where a professional user goes and where nobody else arrives.

The key is the folder path, moved by `app.vault.on("rename")` — already registered in
`src/host.js:233`. The gateway's own `id` cannot serve: it is `folder:${path}?${stableKey(baked)}`
(`src/gateway/obsidian.js`), so two widgets reading one folder through different baked queries hold
different ids and would each ask the same question. A folder has no id of its own to borrow either
— `docs/record-identity.md` gives one to a record, and minting one for a directory would mean
writing into the vault to draw a tile.

## The map is a wrapper gateway

`mappedCollection(base, map)` renames on read and un-renames on write, one symmetric function of the
same shape as `narrowedCollection` in `src/gateway/narrow.ts`. The chain is
`folderGateway → mappedCollection → narrowedCollection`, and the widget reads `habit.days`.

A need answered by a derived value rather than a field is read-only: `update.can()` answers
`{ can: false, reason }` rather than a write that lands nowhere.

## Where a person meets it

In the settings window, under the source it belongs to, and only once a folder is picked:

```
Source · Tasks
  [ Folder ] [ Typed here ] [ From a widget ]
  Orbitask/Tasks                                    ✓

Reading · Tasks                                 3 of 4 found
  Title       ←  name                                  auto
  Due         ←  due-date                              auto
  Status      ←  status                                auto
  Done on     ←  [ pick a date property        ▾ ]   needed
```

Resolved rows are dim and unpressable-looking; the unresolved one is the only bright thing on the
block. Its dropdown holds only fields whose type matches the need, each with its own sample values,
and offers to create the property when the folder holds none.

A **required** need left unresolved is also the tile's own empty state, so a person who never opens
the settings window still meets the one question, in place.

## What this deletes

- `settings.field`, `settings.prop`, `settings.pick` as free text, across `@habit/*`
- `toHabit(row, field)` in `widgets/@habit/grid/widget.tsx`, and its equivalent in every widget
- `manifest.json` as a hand-written file

## Open

- One shape per folder, or per folder and widget family. A folder read as tasks by one board and as
  sources by another is a real case; the tile override is the release valve either way.
- Whether the eight `@habit/*` widgets migrate in one pass. One pass, with `was`, is fewer states to
  test.
