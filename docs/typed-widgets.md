# Types are a build-time fact, not a runtime one

## TL;DR

Widgets move to TypeScript, and the manifest stops being written by hand: `widgetarium build` reads
the types and emits it. The engine keeps injecting by the manifest, because **types do not survive
to runtime** — no transpiler leaves them there, so nothing can read them in a running plugin.

## What is already settled

**TypeScript runs today with one line.** The runtime compiles widgets with sucrase, and sucrase
3.35.0 strips types — verified. Adding `"typescript"` to its transform list is the whole change
needed for a widget to be *authored* in TypeScript and load exactly as it does now.

**Actions already live inside sources — but not in the shape they should have.** The engine does
derive them per source, and a created file lands in that source's own folder, so "a source carries
its actions" is a formalisation rather than a rewrite. What is wrong is the shape: today an action
is TWO fields, `create` beside `canCreate`, `update` beside `canUpdate`. It should be ONE typed
object:

```ts
type Action<Input> = {
	can(input: Input): boolean
	run(input: Input): Promise<void>
}
```

One field, not two, so a caller cannot hold the verb without its permission, and a new action costs
one entry instead of a pair someone has to remember to add. A source may then declare as many as it
likes. **Obsidian only understands a fixed set of names** — add, update, remove; reading is the
source itself — so those names are the contract with the host, not a limit on how many actions may
exist. Anything beyond them is injected, the way a dependency is: the engine knows nothing about it
and passes it through by name.

An unset action is not missing, it is **unavailable**: `can()` answers false and the interface says
so, rather than the caller discovering an absent function.

## The correction that shapes everything else

The wish was that the engine read the props' types and inject accordingly, "like React". It cannot,
and neither does React — React passes props by NAME. Types are erased by every transpiler, ours
included, so a running plugin has nothing to read.

So the line falls here:

```
TypeScript                     the source of truth, written by a person
    |
    |  widgetarium build       reads the types with the TypeScript compiler
    v
manifest.json  ← autogenerated, not edited
widget.js      ← types stripped
widget.d.ts
    |
    |  runtime
    v
the engine injects sources, slots and actions BY THE MANIFEST
```

The manifest does not disappear. It stops being authored and becomes compiled — which is exactly
what earns it an "autogenerated, do not touch" line at the top.

**This is also what makes the interesting feature possible.** "Open a source and see which fields it
has" needs the field list to exist as DATA, because at runtime there is no type to inspect. The
build writes it out of the type the source declares for its records, and the filter and the sort are
then built from that list instead of from guesses. Properties a person adds themselves are appended
to it at runtime; the generated list is the floor, not the ceiling.

## What a contract review found, and what it leaves for the types

A read-only review of the three seams the board block just gained. Four findings were fixed at
once, because they were gaps rather than decisions:

- **A slot got no `board` at all.** The registry resolves the SAME file whether the board placed
  it or another widget slotted it, so a widget written against `props.board.properties` as a tile
  threw on the first property it read as a slot. One shape now, every path.
- **The note's own path never reached a widget.** `renderMarkdown` takes a `sourcePath`, the
  engine knew it at the mount and never passed it on, and the default was the vault root — so
  every wikilink in a rendered body resolved from the wrong place, silently. Bound at the mount
  now, where the path IS known; a widget calls `renderMarkdown(element, markdown)`.
- **`create` threw away the body it had just written.** `update` reported what landed; `create`
  reported nothing. Same rule for both now.
- **Letting go of a render twice unloaded an unloaded child**, and a render landing after the
  release painted into an element its owner had given up.

What is left is one question, and it is a TYPE question, which is why it waits for this pass:

**A write that did not happen is currently indistinguishable from a write that was not asked
for.** `update` returns `undefined` for the body both when a body write was refused and when the
patch carried no body; `update` on a read-only source resolves to `null`, a third shape again;
`configureBoard` and `context.set` return a boolean nobody is obliged to read. Every one of these
is the same failure the person sees as "I saved it and nothing happened".

The `Action<Input>` shape above is where this is settled — `can` answers before the fact, and
`run` must then report what landed in ONE shape, not three. Deciding it before the types exist
would mean deciding it twice.

## Open

**Who runs the build.** The plugin, when it loads a widget — convenient for the author, but it drags
the TypeScript compiler into the plugin. Or the widget's author, before publishing — the plugin
stays light, but every widget gains a build step. Undecided.
